# 后台次数发放

更新时间：2026-10-23。

## 使用方式

1. 用管理员身份打开管理后台 `/entitlements`（本地为 `http://127.0.0.1:5274/entitlements`）。侧栏为“次数发放”，“用户与项目”页面也提供入口。
2. 搜索用户昵称或ID，选择用户，再选择该用户的有效项目。昵称相同时用完整ID区分；用户和项目支持分页。
3. 查看当前可用、预占、已用次数，填写增加次数及原因，点击“确认增加次数”。单笔为1–10000的整数，原因去除两端空白后为1–120字。
4. 成功提示包含发放次数、当次发放后的可用余额和记录ID；下方记录按当前用户/项目筛选，清空用户可查看全部发放。历史试用发放一并展示，旧流水没有的余额快照显示“未记录”。

发放只增加选中项目的`available`，不修改`reserved/consumed`，不启动图片生成。账号级试用活动仍然每期仅一次；人工补发使用独立请求键，不修改试用活动版本或领取记录。补发不代表更改模型能力、主题审核或素材授权，出图仍由用户确认。

## 权限与数据

入口由operations插件装配；管理页面要求operations、commerce、projects已启用。所有读写接口均要求独立管理会话中的`admin`，普通用户及`staff`不可发放、不可读取发放列表。不提供手机号、登录摘要、照片或供应商凭证。

| 方法 | 路径（均以`/api/v1`开头） | 用途 |
| --- | --- | --- |
| GET | `/admin/entitlements/users?q=&offset=0&limit=50` | 按昵称/ID搜索有效客户 |
| GET | `/admin/entitlements/users/{user_id}/projects` | 该客户有效项目及三桶余额，支持offset/limit |
| GET | `/admin/entitlements/grants` | 发放流水，支持user_id/project_id/offset/limit |
| POST | `/admin/entitlements/grants` | 人工补发；提交request_key(UUID)、user_id、project_id、amount、reason |

记录复用commerce的`EntitlementEvent`（kind=grant）和operations的`Audit`（action=`entitlements.grant`）。审计关联流水ID，保存管理员ID、用户与项目ID、原因、次数及发放前后余额；名称在查询时从当前对象读取，避免删除匿名化后再返回旧名称。本次无新增表和迁移。

事务按管理员→目标客户→项目→权益账户加锁；目标客户须为active/customer，项目必须归属于该客户且为active。原子提交余额、唯一流水和操作审计，任何一步失败全部回滚。SQLite使用既有BEGIN IMMEDIATE；PostgreSQL使用行锁，兼容确认生成的客户→项目→权益锁顺序。

每个管理员的request_key只对应一次发放：相同键、相同内容返回原记录及当时余额快照；同键改用户、项目、次数或原因返回`IDEMPOTENCY_CONFLICT`。新一笔有意发放必须使用新键。页面发放中禁止重复提交；断网或5xx保留冻结请求，按管理员ID分区保存在sessionStorage，刷新后“重试本次发放”复用原键；确定的4xx拒绝后保留表单可修改。不保存管理凭证；成功后清除待核对请求。关闭浏览器会话后如需核对，先查发放记录，不能把新请求当作旧请求重试。

本期只补齐增加次数与记录查询，尚未实现撤回次数、批次到期、退款或支付。原开发设计中的revocations仍属规划，不能视为已有接口。
