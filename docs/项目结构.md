service 是业务用例入口。repository 不独立 commit；最外层用例协调一次事务。创建确认单、预占权益、创建任务及 outbox 必须共用同一数据库事务，不能各模块各自提交。

### 5.2 业务表归属

| 目录 | 表 |
|---|---|
| modules/identity | users |
| modules/projects | projects、subjects、subject_references |
| modules/assets | assets、asset_inputs |
| modules/conversations | conversations、messages |
| agents/runtime | agent_runs、agent_steps |
| modules/executions | plan_versions、plan_inputs、execution_approvals |
| modules/media_jobs | jobs、provider_attempts |
| modules/operations | outbox_events、inbox_events、audit_logs |
| modules/commerce | entitlement_accounts、entitlement_events；商业化后 orders、payments、refunds |
| modules/knowledge | knowledge_documents、knowledge_versions、knowledge_chunks |
| modules/feedback | feedback_tickets、feedback_events |
| modules/catalog | V1 代码配置，不强行建配置管理表 |

ORM 关系尽量使用 ID 和字符串引用，避免因跨模块模型相互导入导致启动循环。Alembic env 显式导入模型集合，跨表复合外键和循环外键通过迁移顺序解决。

### 5.3 调用方向

```text
React 页面 → feature → api-client → API 路由
API 路由 → 身份/输入校验 → 业务 service → repository / 外部适配器
Agent Worker → runtime → orchestration → 受控 tools → 业务只读 service
媒体 Worker → media_jobs service → 供应商/存储/渲染适配器
后台 → admin API → 同一套业务 service
```

禁止路线：前端直接调用图片供应商；Agent 直接执行 SQL；后台随意覆盖 Job 状态；repository 内部私自提交跨模块事务；业务模块引用 React 类型。

### 5.4 V1.1 补充职责与部署边界

| 位置 | 新增/细化职责 | 边界 |
|---|---|---|
| agents/context | 每次调用组装、预算与来源记录 | 不把摘要变成业务事实，不复制第二套会话数据库 |
| agents/tools、policies | 工具契约、错误修正和循环终止 | 不增加扣费/发布类 Agent 工具 |
| integrations/governance | 共享额度、能力矩阵、失败分类 | 不决定已批准图片任务能否重发，由 media_jobs 判定 |
| modules/projects + assets | 清理意图、epoch、目标标记、血缘、分批完成校验 | 与 maintenance_tasks 配合；模型不能执行清理 |
| workers/maintenance_tasks | 执行清理、恢复和核对 | 独立 maintenance 队列；scheduler 只扫描投递 |
| observability | 关联标识、阶段耗时、结果与成本口径 | 正文按需授权采集，不能无差别记录敏感信息 |
| releases + evals | 不可变版本、基线、回归和放行证据 | Git 配置与受控报告起步，不新建管理平台 |

后端同一镜像可启动 API、agent、media、knowledge、render、maintenance 和 scheduler 等不同服务；按阶段启用必需进程，低量 knowledge 可合并由 media Worker 消费。共用镜像不等于共用进程、并发槽或内存限额。render 与 maintenance 保留独立执行容量。

## 8. 工程标准

- Python 使用明确类型注解、Pydantic DTO、统一业务异常；重要 JSONB 结构附 schema_version。
- 前端组件 PascalCase，hook 使用 use 前缀，业务目录使用 kebab-case；Python 文件/函数使用 snake_case。
- 时间统一 UTC；UUID 不依赖顺序提供业务先后，消息用 seq、方案用 version_no。
- 数据库修改只通过 Alembic；生产不执行启动时自动 create_all。
- 每个外部调用都有超时、可分类错误和资源限制；是否重试由业务状态决定。
- 日志默认脱敏，不输出 Cookie、手机号原文、对象签名地址、供应商密钥和照片数据。
- PR 必须包含对应契约/迁移变化及必要验证，禁止提交测试照片中的真实个人资料。
- 测试照片与原始知识文档存私有测试资源，Git 中仅存经过授权的样例或引用清单。

README 在工程建立后说明实际可运行的启动步骤、开发账号创建方式、迁移和测试命令；不可把本设计中的目标目录当作已经交付的实现。

### 8.1 项目与模块说明（必需）

- 根 README：项目用途、系统组成、目录入口、环境要求、启动/构建/验证步骤、配置获取方式、文档入口及当前限制。
- apps/web、apps/admin、services/backend、packages/api-client 各自 README：职责、入口、依赖、配置、发布产物及已验证的命令。
- 业务模块和关键基础模块提供简短 README，说明负责/不负责的事项、公开入口、调用方向、数据归属和关键约束；部署和脚本目录说明执行顺序、影响范围与恢复办法。
- 每份设计文档注明用途、版本、审阅/实施状态和配套文档；代码块明确是目标示例还是已验证命令。
- 中文说明为默认；API 名称、标准术语和代码标识保留原文。注释与 README 不写密钥、真实个人数据或未经验证的运行结果。

### 8.2 文件级说明（必需）

所有手写源码、测试、脚本、迁移和可注释配置文件提供文件头，至少说明用途/所属模块及重要边界；存在副作用、运行条件或调用顺序时一并说明。Python 使用模块 docstring；TypeScript/JavaScript 使用块注释；CSS、SQL、YAML、Shell、Dockerfile 使用各自合法注释。shebang、编码声明等必须处在首行时，文件说明紧随其后。

Markdown 使用开头的用途说明或 HTML 注释。JSON、锁文件、二进制等不支持或不应手改注释的文件，通过相邻 README、schema 描述或素材清单记录用途、关键字段、来源/许可；不得为了注释破坏文件格式。生成代码由生成器统一输出来源、生成命令和禁止手改声明；OpenAPI 字段说明从后端 schema 生成，不人工修补 generated 文件。

### 8.3 代码级注释（必需）

- 手写函数、方法、类、组件和 hook 提供 docstring/JSDoc 或紧邻声明的说明，简短代码可用一句准确说明；公开接口补充关键输入、输出、错误、权限和副作用。复杂匿名回调在所在代码块说明意图。
- 关键业务逻辑解释“为什么这样做”：锁顺序、事务所有者、幂等键来源、租约/epoch 校验、未知外部结果、权益转换、清理完成条件和降级限制。
- 状态枚举、难以直观理解的字段和常量解释语义、单位、时区及空值；模型/schema 字段描述同步进入 OpenAPI。数据库表/列在迁移中提供 COMMENT，约束和索引命名体现用途。
- 异步流程注释写清取消、超时、重试和资源释放责任；测试说明所验证的业务行为和故障条件；迁移说明前后兼容性、回填及回退限制。
- 注释解释意图和约束，不要求每一行重复代码。变更行为时同步更新说明，删除失效注释；TODO 必须描述缺口及处理条件，不把 TODO 当作已实现功能。

### 8.4 审查与验收

各阶段检查项目 README、模块职责、文件头、代码级说明、字段注释和测试场景说明是否齐全且与实现一致。开发后可用 lint/docstring 规则辅助检查覆盖，人工复核注释内容的准确性；仅有格式检查通过不代表注释合格。缺少必要说明或出现误导性注释，应在阶段验收前补齐。
