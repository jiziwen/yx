# 映序 · 发布与回滚

版本：V1.2 · 2026-10-23。工程已有本地启动、迁移和验收脚本；本手册的生产发布、备份恢复和零停机目标仍须在目标环境独立演练，不以本地通过宣称生产已部署。

配套：[开发文档](../开发文档.md)、[项目结构](../项目结构.md)、[数据库设计](../数据库设计.md)、[故障与清理](./故障与清理.md)。

## 1. 发布单元与责任

| 单元 | 产物 | 发布边界 |
|---|---|---|
| 用户端 web | 带版本的静态文件 | 独立构建、校验和切换 |
| 管理后台 admin | 带版本的静态文件 | 独立入口与会话，不复用客户登录态 |
| 后端 | 固定摘要的镜像 | API、Worker、scheduler 使用独立服务和启动参数 |
| 数据库迁移 | Alembic revision 与兼容说明 | 每个环境仅一个迁移执行者，失败阻止后续切换 |
| Release/目录/模板 | 固定版本与内容摘要 | 与代码、模型、数据契约共同验证；保留旧任务所需内容 |
| 数据库、Redis、对象存储 | 持久化服务与备份 | 不随应用更新清空、重建或删除卷 |

发布负责人记录版本、变更范围和放行结论；实施时明确迁移执行者、故障处理负责人和回滚决策人，可以由同一名维护者承担。密钥来自运行环境，不进入镜像、静态包和发布记录。

当前工作区以 `/Users/jiwen/Documents/yx` 为根；`参考ui/` 是独立演示项目，不参与正式构建。Docker 构建上下文排除演示、node_modules、本地环境、测试私密素材和历史产物。

## 2. 变更影响与构建

1. web/admin 页面变化分别构建对应应用；共享 api-client、根依赖锁文件和公共构建配置变化时，检查全部受影响应用。
2. 后端接口/DTO 变化先导出 OpenAPI、生成客户端，检查契约差异和两个前端兼容。新增可选字段优先，破坏性变更分阶段迁移。
3. 后端构建同一版本镜像，API、Worker 和 scheduler 不在服务器各自临时安装不同依赖；固定 pnpm-lock.yaml、uv.lock 和镜像摘要。
4. 前端使用内容哈希资源文件；HTML/入口采用可更新缓存策略，保留兼容窗口内旧资源。浏览器中的旧前端可能持续请求，不能只验证最新页面。
5. 每次产物包含 build_id/代码版本；发布清单记录前端版本、镜像摘要、数据库 revision、Release、契约版本和配置摘要，不保存秘密值。

## 3. 发布前门禁

- 通过受影响范围的构建、类型检查、必要测试和契约校验；权限、权益、幂等、隐私和状态机关键测试不得带失败放行。
- 模型、提示词、工具、检索或模板变化附基线对比报告，说明样例覆盖、关键失败、成本、时延和人工结论；门槛未确认时不得标记通过。
- 检查项目说明、文件头、函数/组件和关键逻辑注释与实现一致，字段说明已同步 schema/迁移。
- 在测试环境验证新旧前端/API 兼容及旧 Run/Job 恢复；禁止用生产付费请求作无控制的回放样本。
- 明确本次迁移所需锁、耗时、回填、兼容范围和中断窗口；重大迁移先在恢复副本演练。
- 验证数据库备份可恢复、对象版本/生命周期策略有效；备份包含必要元信息及删除/撤销清单。确认恢复点和恢复耗时目标，未实测不得承诺。
- 检查生产 mock 拒绝、密钥注入、Cookie/CSRF、管理员权限、私有存储和 SSE 代理配置。

## 4. 旧任务兼容策略

发布前从 PostgreSQL 查询旧版本全部非终态 Run、Job、未决 provider_attempt、待处理 inbox/outbox 和隐私清理，记录数量与所需契约。队列为空不代表业务已排空，等待外部结果的任务可能仍持续很久。

| 情况 | 发布方式 |
|---|---|
| 新代码兼容旧任务和 schema | 新 Worker 按冻结版本继续执行；不能用最新模板重解释旧输入 |
| 新旧 Worker 共存 | 按版本路由或领取时验证 supported contract/release；不兼容 Worker 不得领取，未支持任务保留并告警 |
| 无法兼容且可等待 | 暂停相关新任务入口，旧 Worker 继续执行至业务非终态清空；提前说明维护窗口 |
| 未决外部任务短期无法排空 | 保留兼容旧代码的核对/回调处理能力，或推迟本次破坏性变更；不得强制改成功/失败以完成发布 |

长时任务记录保持在数据库；发布不重置 attempt_no、累计预算、deadline 或 supplier submission_no。旧 Worker 失去租约后不能最终提交，迟到回调仍先持久化到 inbox 再按任务版本核对。

清理 Worker 的状态 schema 也要兼容；发布过程中保留隐私访问屏障与维护容量。旧版本不理解新清理状态时不能强行执行或跳过。

## 5. 执行顺序

1. 记录发布清单、当前健康指标和可回退版本，确认负责人及故障停止条件。
2. 构建并保存不可变产物，先在测试环境完成验证；生产拉取相同摘要，禁止用浮动 latest 代替清单。
3. 备份并验证恢复准备，由唯一执行者运行向前兼容的扩展迁移；回填按可恢复批次执行。迁移失败停止切换。
4. 依据第 4 节安排兼容 Worker、回调和调度器，再更新 API。服务启动先完成配置/数据库兼容和就绪检查，才开放新流量与任务领取。
5. 发布受影响前端并验证浏览器旧版本兼容；发布 Release 时仅切换新任务的默认版本，既有任务保留冻结配置。
6. 检查关键用户链路和运行指标；异常时暂停扩大发布范围，按第 7 节处理。
7. 经过约定观察窗口、旧任务完成及回退窗口结束后，才删除旧代码/模板支持和旧 schema 字段；清理迁移是后续独立变更。

单机 Docker Compose 替换可能短暂中断。若业务要求零停机，需要额外的双实例流量切换、容量与数据库兼容演练，不能只凭 restart policy 宣称零停机。

## 6. 切换后的验证

| 检查 | 通过证据 |
|---|---|
| 静态入口 | 两端可加载；旧资源仍可访问；管理登录与客户登录隔离 |
| API | 健康/就绪正确，数据库 revision 匹配，未启用开发身份 |
| 业务闭环 | 受控测试账号可创建固定方案、确认与查询；重复确认不重复预占 |
| 异步处理 | Worker/scheduler 心跳、领取、回调和核对正常；无异常积压和版本拒领 |
| SSE | 订阅就绪→快照→事件合并通过；重连、丢通知校准、退出后断流符合约定 |
| 清理 | 维护队列有容量，隐私屏障未被解除，迟到对象不被发布 |
| 观测 | request/run/job/trace 可关联，成本和错误率无异常，日志无敏感正文泄漏 |

生产冒烟仅使用专用账号及受控、已授权素材；真实付费调用需按批准测试预算执行，记录产生的任务和费用。发布验证不修改真实用户余额或覆盖生产任务状态。

## 7. 回滚与失败处理

1. 判断故障属于前端、API、Worker、Release、迁移还是供应商；暂停受影响新任务，保留读取、回调、核对和清理能力。
2. 前端回退到已保存产物，确认后端仍支持旧契约；不删除仍被浏览器引用的静态资源。
3. 后端/Release 回退前核对数据库与当前任务契约。旧代码无法理解新任务时，仅把新任务入口切回已知版本，保留新版本兼容处理者或暂停并修复；不直接让旧 Worker 消费新任务。
4. 数据库默认保留兼容扩展字段，采用向前修复。涉及丢数据的 downgrade 不能作为默认回退；任何恢复备份必须先评估恢复点后的新增数据和外部付费事实。
5. 回滚不撤销外部已提交生成，也不自动返还所有权益；按每个 Job 的事实和状态机处理，避免重复付费或重复结算。
6. 记录影响范围、异常版本、采取动作、数据/任务核对结果和后续回归样例。

## 8. 备份恢复演练

在隔离环境恢复数据库，核对对象引用、权益流水、供应商未决提交、inbox/outbox、清理 tombstone 和版本文件。外部系统不会随数据库一起回到过去，恢复后先冻结付费提交并核对恢复点后的外部请求。

保留独立、受访问控制的删除/撤销清单及覆盖窗口，避免从旧备份恢复已删除资料后重新对外展示。恢复环境默认不可公开访问，也不自动启动生产付款/生成或发送任务；重放清理与核对完成后再开放。记录实际恢复点损失范围和耗时，作为后续目标依据。

## 9. 实施时需落地的入口

开发阶段将已验证的构建、健康检查、迁移、队列暂停/恢复和版本切换命令写入各模块 README，并在此链接。当前不提供虚构服务名、生产地址和可直接执行的发布脚本。新增脚本必须有用途、参数、副作用、失败处理和恢复方式注释。
