# 映序 · 故障与清理

版本：V1.1 · 2026-10-21。状态：待用户审阅；流程尚待开发和演练。当前仅修订文档，用户审核通过并同意开发后实施。

配套：[开发文档](../开发文档.md)、[数据库设计](../数据库设计.md)、[项目结构](../项目结构.md)、[发布与回滚](./发布与回滚.md)。

V1.4 实施入口：当前 M1 图片任务使用 reconciliation_required 状态。管理端“生成任务→查看详情”展示稳定请求键、凭据是否保存、错误、用量与未知/确认费用，并受控查询原任务；无接单凭据不提供强制结算。302.AI 有凭据任务由本地 Worker 或 Celery reconcile 查询恢复。共享账号协调使用数据库 runtime_gates，429 的 Retry-After 与连续失败熔断分别保存，其他在途任务成功不会提前解除供应商退避。下文仍含后续阶段设计（完整清理租约、回调 inbox、人工工单等），实际边界见 [M1 接入与恢复](../M1供应商与任务恢复.md)。

## 1. 处理原则与定位入口

先通过 request_id、run_id、job_id、provider_attempt、trace_id 定位事实，核对版本、租约、期限、累计预算、外部请求键和隐私状态。日志只提供脱敏摘要；需要素材或对话时走已有授权入口，不因排障获得任意用户照片访问权。

数据库负责状态，Redis 消息和 SSE 仅是调度/通知。故障处置通过受控服务命令或后台操作，记录操作者、原因、动作键及结果；不能直接把 running 改 succeeded、重置预算或覆盖权益流水。相同恢复动作使用稳定幂等键。

## 2. 常见故障处置表

| 情况 | 自动处理 | 人工升级与禁止动作 |
|---|---|---|
| 对话模型限流/超时 | 分类退避，在总预算内使用已评测候选；失败给表单/人工入口 | 不无限重试，不混拼不同尝试流输出 |
| 图片提交超时、遗留 submitting | 标记未知，按原请求键/任务号核对 | 不能创建新付费提交碰运气；无查询能力需供应商/人工确认 |
| 图片已明确失败 | 按冻结策略、剩余预算有限重试，最终失败释放预占 | 不修改原批准规格，不抹去失败尝试成本 |
| 回调早于响应 | 验签持久化为 unmatched，后续匹配原 attempt | 不因暂未匹配就丢弃或反复发起生成 |
| 重复/迟到回调 | inbox 去重，按状态机和隐私版本应用 | 已终结任务不自动重开，旧结果不再次核销 |
| Worker 崩溃/租约过期 | 扫描器受控接管，attempt_no 递增，旧执行者失权 | 不重置 deadline、预算或 submission_no |
| Redis 丢失/不可用 | 暂停新付费准入，从数据库恢复未决任务和额度占用 | 不将通知丢失当作任务失败，不清空数据库状态 |
| 文件存储/下载失败 | 保留阶段和尝试，限次重试；临时文件隔离 | 未验证可交付文件前不核销权益 |
| RAG/embedding 异常 | 保留旧发布知识，暂停新索引；经评测的关键词检索可降级 | 不展示草稿，不编造缺失证据 |
| 视频占满资源 | 独立 render 并发/资源限额，暂停新渲染或排队 | 不占满 API、交付和 maintenance 容量 |
| SSE 丢事件/断线 | 订阅就绪后快照合并，活跃任务低频校准 | 不把前端进度当作任务事实 |
| 隐私清理失败 | 保持访问屏障、持久化进度、限次重试 | 超限升级，不能手工把 pending 改 false |

## 3. 供应商未知结果核对

1. 读取 provider/account_key、client_request_key、provider_task_id、提交时间、请求摘要和已验签回调。
2. 根据能力矩阵选择查询方式，退避重查；“暂未查到”不等于供应商明确未受理。
3. 查询到接受/运行：关联既有 attempt，继续等待；查询到成功：校验文件、执行资格和隐私后尝试交付。
4. 确认失败/取消：按 Job 状态机结束或在冻结预算内重试，权益变更与状态和流水同一事务。
5. 超过核对告警期限或供应商不支持可靠查询：保持 needs_reconcile，暂停该任务新的付费提交，展示“待核对”，提供人工入口。记录处理负责人、下次复核时间和依据；不能让任务无负责人无限等待。
6. 人工结果仍未知时可按产品明确政策作补偿，但补偿作为独立授权业务操作，不能伪造供应商失败或释放原预占后偷偷重发。V1 若没有该政策，保持待核对并向用户说明。

核对任务也受账号级额度和调用超时限制；查询重试不增加 submission_no。人工记录可存脱敏 audit_logs，并更新既有任务/attempt 的复核时间，不必先建设独立工单系统。

## 4. Worker、队列与状态恢复

scheduler 扫描长期 queued、到期 retry_wait、失效租约、待核对 attempt、未完成 inbox/outbox 和清理项目，以有界批次投递。即使 outbox=sent，资源长期无进展仍应检查数据库执行资格；不能仅依赖 Celery 结果后端。

领取、心跳和最终写入均验证 owner/attempt/有效租约；网络调用和文件处理不占用长数据库事务。领取前检查契约/Release 兼容，不能执行的版本保留并告警。无效或格式不符消息隔离记录原因，停止反复毒消息循环，不静默丢弃对应业务资源。

供应商账号额度在多 Worker 间共享；Redis 恢复后先核对数据库中的在途/未知请求再恢复准入。内部并发许可过期只表示本地许可失效，不证明外部生成已结束。用户排队上限统计数据库非终态记录，公平调度与限额需要并发测试。

维护任务由独立 maintenance Worker 执行，scheduler 不直接做大文件删除或长查询。清理状态保存在 projects，不把清理任务硬塞进仅支持 knowledge_index 的 system Job。

## 5. 隐私清理流程

### 5.1 触发与阻断

适用场景：账户/项目删除、人物授权撤销、敏感素材删除。普通取消选中参考图不触发隐私删除。

在短事务内持久化目标标记，递增项目 privacy_epoch，设置 privacy_cleanup_pending，写清理状态/下一次执行时间、取消请求、outbox 和审计。账户删除先禁止登录和新项目创建，再对所属项目执行流程；各项目结束且账户敏感字段完成处理后才标记账户 deleted。

访问接口、上下文构建、方案确认、Worker 领取和交付都复核隐私条件。后台看图授权、缓存和长连接不得绕过屏障；既有短时链接按已确认的对象失效/代理策略处理，不承诺普通签名链接能天然即时撤销。

### 5.2 可恢复执行

1. 领取项目清理租约，记录当前 epoch 和单调递增的 cleanup_attempt_no。
2. 从撤销人物、删除标记及输入血缘发现目标，先保留持久标记和关系，再分批擦除。
3. 删除原图/派生图/缩略图/视频、关联附件、上下文快照/摘要、任务临时文件、获授权评测副本及敏感报告引用。私有知识材料如被纳入目标，也需清除原文/片段/向量及缓存。
4. 每次外部删除后以短事务提交阶段和游标；已不存在对象按幂等成功处理。事务失败后重做同批，不跳过未确认目标。
5. 进度更新校验 epoch + worker_id + attempt_no + 租约。新撤销到达时增加 epoch、合并持久目标并重置游标；旧执行者不得解除屏障。
6. 失败持久化错误和 next_attempt_at，限次退避；超过门槛进入 blocked，保留屏障并告警。授权维护者修复原因后通过受控服务重新入队并审计。

### 5.3 完成条件

仅当当前 epoch 的目标发现和擦除完成、敏感快照和副本已处理、相关访问凭证满足失效策略、旧 Worker 无法发布结果，才能通过业务服务清除 privacy_cleanup_pending。删除项目保持不可访问；局部素材删除后，仅未受影响且仍获授权的资源恢复可用。

清理完成不代表供应商费用已结清，也不代表未知外部请求已取消。外部请求由核对流程继续处理；供应商侧数据删除按实际能力和约定跟踪，未确认时不得记录“全部外部副本已删除”。最小内部 tombstone 保留必要 ID、版本、删除时间和审计依据，不保留照片本体、手机号或完整对话。

### 5.4 迟到文件、孤立对象与备份

下载/渲染临时对象使用 job/attempt/epoch 关联命名和创建时间。交付事务复核当前授权；失败留下的对象由孤立扫描处理。扫描需排除有效租约下的正常临时对象，设置实测安全宽限；清理完成后仍持续扫描迟到垃圾，不允许其重新成为 ready Asset。

原始上传使用短时、受大小/对象键限制的凭证；撤销期间无法立即失效的上传凭证，要等待失效并再扫对应对象，防止“删完又上传”。临时对象生命周期是兜底，不能代替权限阻断和显式清理。

备份有独立保留策略和访问控制；记录删除/撤销清单，恢复旧备份后先应用清单和隐私屏障再开放流量。保留期、供应商删除能力、链接最长有效期和存储生命周期在对外测试前明确，形成可核验配置。

## 6. 观测、告警与人工操作

至少监测：最老 queued 等待时间、租约过期数量、未知提交持续时间、重复失败次数、outbox/inbox 积压、清理最老等待时间、blocked 清理、供应商 429/错误率、成本异常和维护队列容量。

具体阈值在试运行后确认并版本化；触发告警须关联资源 ID、版本、错误类别和处理入口，不附原图、签名 URL、完整对话或密钥。每类告警明确负责人、下次复核时间和恢复条件；告警系统不是业务状态来源。

后台/维护入口仅提供受控动作：暂停新请求、重查外部事实、重投递已有任务、恢复清理、按现有规则取消。动作必须校验角色、当前状态、幂等键和版本，并记录审计。不得提供任意 SQL、覆盖 Job 状态或绕过原授权重新生成的通用按钮。

## 7. 验收与回归样例

开发阶段至少演练以下场景，记录初始状态、故障注入点、恢复动作和最终事实：

- 供应商已接受，但响应丢失；恢复后没有第二份付费提交。
- Worker 失去租约后迟到返回；旧 Worker 不能覆盖新状态。
- 回调先到、重复到、取消后到；不重复交付或核销。
- Redis 重启后任务恢复、额度保守重建，不出现无控制的新调用。
- 两个清理 Worker 竞争，清理中新增撤销，对象删除后数据库提交失败。
- 清理结束后迟到文件/旧上传凭证写入；访问仍被阻断并可回收。
- SSE 快照期间完成任务、连接正常但通知丢失、退出后旧连接存在。
- 视频高负载时仍有 API、交付与清理执行容量。
- 恢复旧备份后已撤销内容不会重新开放，外部付费事实经核对后再恢复提交。

关键故障样例纳入固定回归集，受影响版本发布前执行。测试与恢复脚本必须注释说明故障条件、预期不变量、操作副作用和清理方法；本轮不创建这些脚本。
